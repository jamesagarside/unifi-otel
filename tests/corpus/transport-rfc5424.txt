# SYNTHETIC. The third axis from issue #25: the same payload over
# RFC3164/UDP and over RFC5424/TCP.
#
# MATCHED-PAIR FILE. Frames come in adjacent pairs: the RFC3164 frame
# first (replayed over UDP to syslog/unifi_udp), the RFC5424 frame second
# (replayed over TCP to syslog/unifi_tcp). The harness routes each frame
# by its own syntax -- "<PRI>1 " means RFC5424 -- so the two receivers are
# both exercised from one file.
#
# WHY THIS AXIS EXISTS: RFC5424 has no doubled-hostname pathology, so
# every RFC5424 frame takes what is effectively the single-hostname path
# -- the exact path issue #24 showed was silently degraded. It was never
# replayed before.
#
# The RFC3164 member of every pair carries a SINGLE hostname. RFC5424 has
# no doubled-hostname shape, so pairing a doubled frame against one would
# vary two axes at once; the harness refuses it.
#
# HONESTY NOTE: NO RFC5424 FRAME OF ANY KIND HAS EVER REACHED THIS
# PROJECT. The seven-day capture behind the real-*.txt files contains
# zero of them -- the gateway it came from has its SIEM Server set to
# UDP. UniFi's SIEM Server offers RFC5424 over TCP as an option, and that
# is the whole of what is known: not that it has been seen, and not what
# it looks like. Whether UniFi emits non-CEF device syslog over 5424 at
# all is an OPEN QUESTION (#25).
#
# So every frame below is an invention. What they can honestly prove is a
# property of THIS CONFIG -- that a well-formed RFC5424 frame carrying a
# known payload comes out of the pipeline as the same record its RFC3164
# twin does. What they cannot prove is that UniFi ever sends one, or that
# it looks like this if it does.
#
# THE ONE ASSUMPTION MOST LIKELY TO BE WRONG is the APP-NAME on pair 5.
# It is set to the literal "CEF" because that is what the RFC3164 parser
# derives from a CEF frame's "CEF:" tag, and it makes the pair agree.
# Measured against 0.157.0, the CEF path over RFC5424 turns entirely on
# that field:
#     APP-NAME "CEF"      -> no process name, no process pid (matches UDP)
#     APP-NAME "-"        -> no process name, no process pid (matches UDP)
#     APP-NAME a real one -> process name AND process pid ARE set, which
#                            the UDP twin never has, and bar 5 would fail
# That last row is not a bug -- a real app name is real information --
# but it means pair 5 is green because of a value somebody chose, not a
# value anybody measured. A real capture settles it; see the RFC5424
# section of docs/contributing-samples.md for how to take one.
#

#
#    That matters because 1b is the half of section 1 that issue #24 was
#    about. The RFC5424 frames above all exercise 1a, which is where the

#    colon in "warning:".
